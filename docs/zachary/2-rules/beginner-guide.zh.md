# 对接清单·新手讲解版

> 配套文件：`api-contract.md`（给 AI 读的精简版）。
> 这份是给**你**读的：把里面每个概念、每一节讲到你能看懂、能检查。比赛时你不需要背，只需要看得懂、能判断 AI 写的对不对。

---

## 第 1 部分：先搞懂 8 个词

| 词 | 大白话 | 这个项目里的例子 |
|---|---|---|
| **函数** | 一段"做某件事"的代码，有名字、有输入、有输出。就像一个按钮，按下去会干活。 | `confirmAttendance(...)`：保存点名 |
| **输入（参数）** | 调用函数时交给它的信息 | 哪节课、每个学生到没到 |
| **返回值** | 函数做完后交回来的结果 | 保存好的出勤记录 |
| **类型（type）** | 对"一份数据长什么样"的描述：有哪些字段、各是什么种类（文字/数字/日期） | `{ name: 文字, price: 数字 }` |
| **Zod** | 一个代码库，用来**检查**收到的数据符合不符合类型。不符合就拒绝 | 老师提交的课程名是空的 → Zod 拦下来 |
| **actor** | "现在是谁在操作"，包含用户 ID 和角色（老师/学生）。**只能从登录状态里取，不能听前端或 AI 说** | `{ userId: "abc", role: "TEACHER" }` |
| **提案（Proposal）** | AI 想做某件事，但还没做，先存成一份"预览单"，等老师确认 | "AI 打算建一门周三数学班，学生是小王、小李" |
| **唯一约束** | 数据库层面的规则："这两个字段的组合只能出现一次"，重复写入会被数据库自己拒绝 | 同一个学生同一节课，只能有一条扣课记录 |

再补两个：
- **API**：程序之间"怎么互相调用"的约定。我们项目里的 API 主要是两类：① 后端**函数**（Nick 写的，AI 确认接口来调用）；② 少数**网址接口**（比如你写的 `/api/ai/chat`、`/api/ai/confirm`，页面通过它们跟 AI 说话）。
- **schema / Prisma**：数据库里"有哪些表、每张表有哪些列"的说明文件，Nick 负责。

## 第 2 部分：整个系统怎么跑（一张图）

```
老师在网页对 AI 说话："给周三的课点名，小王到了，小李请假"
        │
        ▼
 ① 你的 AI（读）  ──调用只读函数──▶  Nick 的函数  ──▶  数据库（只读）
        │               listMyStudents / listAttendance …
        ▼
 ② AI 生成一份"提案"，存进 AgentProposal 表（状态 pending）
        │
        ▼
 ③ 网页显示预览："小王 到课；小李 请假。确认吗？"
        │  老师点【确认】
        ▼
 ④ 你的确认接口：
      a. 把提案状态 pending → confirmed（只能成功一次，防止重复）
      b. 检查数据格式（Zod）
      c. 调用 Nick 的函数 confirmAttendance(actor, {...})
        │
        ▼
 ⑤ Nick 的函数：检查权限 → 保存出勤 → 写扣课记录 → 返回结果
        │
        ▼
 ⑥ 你的接口：提案状态改成 executed，把结果显示给老师
```

**关键点：**
- AI 在①②只能"看"和"出预览"，**碰不到数据库写入**。
- 真正改数据的只有⑤，而且必须老师点了确认。
- Nick 的函数不知道"AI"和"提案"的存在，它只是一个普通函数，**手动表单也能调用同一个函数**。

## 第 3 部分：逐节讲解对接清单

### §0 三条总规则
1. **身份只来自登录。** 如果函数接受"前端传来的 userId"，任何人都能冒充别人。所以函数里的 actor 必须由服务器从登录状态取出。
2. **AI 只能读和出提案。** 这是整个产品"可信"的核心，也是评委会看的亮点。
3. **Nick 的函数不认识提案。** 让他的工作更简单，也让手动表单能复用。

### §1 通用类型
```ts
type Result<T> = { ok: true; data: T } | { ok: false; error: {...} }
```
意思是：**每个函数返回的结果只有两种**：
- 成功：`{ ok: true, data: 结果内容 }`
- 失败：`{ ok: false, error: { code: "FORBIDDEN", message: "你无权操作这门课" } }`

好处：调用方永远用同一种方式判断成功失败，不用 try/catch 到处包。

错误代码含义：

| code | 什么时候 |
|---|---|
| FORBIDDEN | 没权限（比如老师想看别的老师的学生） |
| NOT_FOUND | 找不到（课程 ID 不存在） |
| VALIDATION | 输入格式不对 |
| CONFLICT | 冲突（排课时间撞了） |
| INTERNAL | 其他意外错误 |

### §2 数据表
看成几张 Excel 表：
- **User**：所有人（老师和学生都在里面，用 role 区分）
- **Course**：课程，属于某位老师
- **Enrollment**：谁加入了哪门课（学生和课程的"关系表"）
- **Session**：每一节课（时间、状态）
- **Attendance**：某节课某个学生到没到
- **Deduction**：某节课某个学生扣了几次课
- **CourseUnit / Material**：课程单元和里面的资料
- **AgentRun / AgentProposal**：你的 AI 用的两张表：运行记录、待确认提案

**粗体的"唯一"**（比如 Attendance 的 `(sessionId, studentId)`）：保证同一个学生同一节课只有一条出勤。这样即使老师连点两次确认，数据库也不会写出两条，也不会重复扣课。

### §3 只读函数（AI 的"眼睛"）
AI 想回答"我明天有哪些课？"，就调用 `getTeacherSchedule`。这些函数**只查不改**，所以 AI 可以直接调用。

每个函数都有权限检查：老师只能查到**自己**的课程和**已加入自己课程**的学生。

### §4 写入函数（Nick 的"手"）
这些函数会修改数据。**AI 不能直接调用**，只有老师点了确认之后，你的确认接口才会调用。

几个要点：
- **重复调用不重复写**：连点两次确认，不会建两门课、不会多扣一次课。
- **扣课规则**：到课或旷课扣 1 次；请假不扣；每个学生每节课最多一条。
- 冲突时（比如排课时间撞了）：返回 `ok: false, code: "CONFLICT"`，不写入。

### §5 提案类型（你负责）
每种 AI 能提议的事，对应一种提案。提案里存的内容，**就是**对应写入函数需要的输入。

例：`MARK_ATTENDANCE` 提案 = `{ sessionId, records: [{ studentId, status }] }`，确认时原样交给 `confirmAttendance`。

Zod 代码就是用来**检查**这份内容的：AI 偶尔会生成错误格式（比如 status 写成"出席"而不是 PRESENT），Zod 会拦住，不让错误数据流进数据库。

### §5 的确认接口流程（你写的核心逻辑）
1. 确认你是登录的老师，且这份提案是你的
2. **原子地**把状态从 pending 改成 confirmed。"原子"意思是：同一瞬间两个请求同时来，只有一个能成功。第二个失败，直接返回已有结果。这就是"重复点击不重复执行"的实现。
3. 用 Zod 检查内容
4. 调用 Nick 的函数
5. 成功写 executed，失败写 failed 并把错误展示给老师

### §6 AI 工具清单
- 老师的 AI：能查课表、学生、出勤、资料、冲突；能出 5 种提案
- 学生的 AI：只能查自己的工作区和课程资料

学生的 AI 工具更少，因为学生权限更小。

### §7 种子数据
"种子数据"就是**预先放进数据库的假数据**，让你们不用手动录入就能测试和演示。
- Nick 的 seed：只放账号（2 位老师、3 名学生），**课程是空的**，演示从空开始。
- 你的 seed-ai：完整数据（课程、资料、冲突的场次……），**备用**：如果现场 AI 建课失败，一条命令就能导入完整数据继续演示。
- 数据里**故意**放几个"陷阱"：资料里没有的知识点（测试"暂时没有"）、另一位老师的学生（测试权限隔离）、有冲突的场次（测试冲突提示）。

### §8 环境变量
放"密钥和配置"的地方，比如 AI 的 API Key。只放本地 `.env` 文件，**不能提交到 Git**，否则密钥泄露。`AI_MOCK=1` 是备用开关：模型挂了就用预设回答继续演示。

### §9 文件所有权
谁的文件谁改。你不碰 Nick 的目录，他不碰你的。想改对方的东西，走 §10 登记。

### §10 变更记录
一张表，每行记一次改动。**这是防止"悄悄改导致对不上"的唯一办法。**

## 第 3.5 部分：一个完整例子（AI 建课程）

**老师说：** "新建周末数学小班，把小王和小李加进来。"

**① AI 读数据：** 调用 `listMyCourses`（看有没有同名课）。

**② AI 生成提案**（存进 AgentProposal，status = pending）：
```json
{
  "type": "CREATE_COURSE",
  "payload": {
    "course": { "name": "周末数学小班", "subject": "数学", "type": "SMALL_CLASS" },
    "studentEmails": ["wang@example.test", "li@example.test"]
  }
}
```

**③ 网页展示预览：** 课程名、类型、两个学生邮箱，下面一个【确认】按钮。此时数据库里**没有**这门课。

**④ 老师点确认，** 你的确认接口依次执行：
- `createCourse(actor, { name: "周末数学小班", ... })` → 返回 `{ courseId: "c1" }`
- `addExistingStudentToCourse(actor, { courseId: "c1", email: "wang@example.test" })`
- `addExistingStudentToCourse(actor, { courseId: "c1", email: "li@example.test" })`

**⑤ 结果：** 提案变 executed，网页显示"已创建，加入 2 名学生"。老师的课表页能看到这门课了。

**如果小李的邮箱没有注册账号：** 第三个调用返回 `ok: false, NOT_FOUND`。你的接口把结果展示给老师："小王已加入，小李的邮箱未注册"。课程已建好，不回滚（演示版够用）。

## 第 4 部分：你需要真正掌握的（最小集合）

| 你需要会 | 做到什么程度 |
|---|---|
| 看懂一个函数的输入和输出 | 能对照清单检查 AI 写的代码名字、字段对不对 |
| 知道 AI 不能直接写数据库 | 看到 AI 写了 `prisma.xxx.create(...)` 在你的目录里，立刻让它改 |
| 知道提案流程 | 能向评委讲清楚"提案 → 确认 → 函数执行" |
| 知道"重复确认不重复写" | 能演示连点两次确认只生效一次 |

**其他细节让 AI 写，你只需要检查。**

---

## 第 5 部分：检查 AI 写的代码是否符合清单（5 个问题）

每次 AI 写完一步，你问自己：
1. 函数名和字段名，和清单**一字不差**吗？
2. 有没有出现清单里**没有**的函数或表？（有的话，让 AI 删掉或先登记）
3. actor 是不是从登录状态取的，而不是从请求里拿的？
4. 写入前有没有经过"提案 → 确认"？有没有绕过去直接写？
5. 重复调用会不会重复写？

## 第 6 部分：常见错误

| 错误 | 后果 | 避免 |
|---|---|---|
| 自己偷偷改了字段名 | 对方代码全部报错 | 先登记再改 |
| AI 直接 `prisma.attendance.create` | 绕过权限和扣课规则 | 规则文件里禁止；review 时搜 `prisma.` |
| 前端传 userId 给函数 | 能冒充别人 | actor 只来自会话 |
| 没做重复检查 | 老师连点两次扣两次课 | 唯一约束 + 原子状态更新 |
| 密钥写进代码提交到 Git | 密钥泄露 | 只放 `.env` |
| Zod 类型改了没通知对方 | 确认时报错 | 提案类型冻结后只增不改 |

## 第 7 部分：比赛时怎么用

- **H0–1**：两个人对着清单一节一节确认，有疑问当场改，然后冻结
- **每一步开发前**：让 AI 先读 `docs/api-contract.md` 和 `CLAUDE.md`
- **每 90 分钟**：花 2 分钟对照"我做的函数/调用和清单一致吗"
- **想加东西**：写进 §10，对方确认，负责人来改
